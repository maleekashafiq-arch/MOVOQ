# ADR 001 — Offline Sync & Backend Source of Truth

Status: Accepted

Date: 2026-05-02

## Context

MOVOQ is a reward-based fitness application where users earn points through steps and rewarded ads, and redeem those points for rewards and lucky draw tickets. Points have real-world value, so strict backend control is required to prevent fraud, duplication, and inconsistencies. Mobile devices may operate offline temporarily but cannot be trusted for financial or reward-related calculations.

## Decision

### Backend authority

- Backend is the **only** source of truth for:
  - Points
  - Wallet balance
  - Rewards
  - Reward redemptions
  - Lucky draw tickets
  - Coupon/code distribution

- Mobile app **must not**:
  - Calculate points
  - Update wallet balance
  - Confirm rewards or tickets
  - Assume success of any transaction

- Mobile app acts only as:
  - Data collector (steps, ad events)
  - UI renderer

### Step processing

- Mobile collects step data (online or offline).
- Mobile sends step data to backend.
- Backend validates:
  - Daily limits
  - Target completion
  - Fraud signals
- Backend calculates and awards points.
- Backend returns updated wallet balance.

### Rewarded ads vs forced ads

- **Rewarded ads:**
  - Require `AdSessionId` generated by backend.
  - Award points only after backend validation.

- **Forced ads:**
  - Do **not** require `AdSessionId`.
  - Generate **no** points.
  - Identified by UI/placement configuration.

### Reward redemption

- Mobile sends redemption request to backend.
- Backend validates:
  - Reward is active
  - Availability (coupon/code/stock)
  - User has sufficient points
- Backend deducts points and assigns reward in a **single transaction**.
- Backend returns confirmation and reward details.
- If validation fails → **no** points deducted.

### Lucky draw tickets

- Mobile sends ticket purchase request.
- Backend validates:
  - Draw is active
  - User has sufficient points
- Backend deducts points and creates ticket entry.
- Backend returns ticket confirmation.

### Offline sync rules

- Mobile may queue step data offline.
- Each request must include `CommandId` (UUID v4 generated by mobile).
- Backend processes requests **idempotently**.

- If duplicate `CommandId` is received:
  - Backend returns success response.
  - **No** duplicate points are awarded.

- Offline data older than **12 hours** must be rejected.
- Age must be calculated using **server receipt time**, not device timestamp.
- Device timestamp is metadata only.

- The 12-hour offline window is an **MVP** decision and may be reduced in future versions.

### CommandId retention

- Backend must retain processed `CommandId` values for **7 days**.
- Required to handle:
  - Network delays
  - Retry attempts
  - Duplicate submissions
  - Edge cases in distributed systems

### Validation and failure handling

- All invalid requests must be rejected with clear error responses.
- **No** silent failures.
- **No** points awarded for invalid requests.
- All rejected and suspicious actions must be logged.

### Fraud signals (MVP triggers)

`FraudSignal` records must be generated for:

- Steps exceeding daily cap
- Duplicate `CommandId` reuse
- Ad completion without valid `AdSessionId`
- Offline submissions with inconsistent timestamps
- Abnormal step spikes

- Fraud signals must be logged (MVP: silently from the user’s perspective).
- **No** immediate blocking in MVP unless hard validation fails.

### Wallet and ledger

- All point changes must go through `PointsLedger`.
- Wallet balance must always be derived from the ledger.
- Mobile must rely **only** on backend responses for wallet state.

### UI behavior rule

- Mobile must **not** show final state until backend confirms.
- Use pending/loading states for:
  - Step sync
  - Reward redemption
  - Ticket purchase
- **No** optimistic updates for wallet in MVP.

### Future considerations

- Outbox pattern may be introduced later for reliability.
- Fraud detection rules may evolve based on real user behavior.
- Offline window may be reduced in future versions.

## Consequences

- All reward-related actions require backend confirmation.
- Increased dependency on network for financial operations.
- Mobile UX must handle latency using loading states.
- Offline capability is limited to data collection only.
- Strong fraud protection and financial consistency.
- Slight delay in user feedback due to server validation.

## Implementation Rules

- Enforce UUID v4 `CommandId` in all sync APIs.
- Store `CommandId` with 7-day retention.
- Use database transactions for all financial operations.
- Return updated wallet balance in all relevant responses.
- Never trust client-side calculations.
- Reject offline data older than 12 hours using server time.
- Implement idempotent processing for all commands.
- Log fraud signals without blocking users in MVP.
